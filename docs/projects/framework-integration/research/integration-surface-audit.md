## Insights

### 1. Public/guest sharing of charts and dashboards — verified in code, shipped

**Routes** (src2; legacy v2 `src/` was removed in commit `0abeb72f` "refactor!:
remove v2 code" — nothing lives there anymore):

- `frontend/src2/router.ts` — `/shared/chart/:chart_name` → `SharedChart.vue`,
  `/shared/dashboard/:dashboard_name` → `SharedDashboard.vue`; both
  `meta: { isGuestView: true, hideSidebar: true }`, the router guard lets guests
  through on these routes.
- Server side, `InsightsPageRenderer` (`insights/utils.py:165`) renders the SPA
  page for paths starting `/insights/shared` and `/insights/public`
  (`/public` is vestigial — no such route exists in src2).

**Permission model — a boolean flag, no tokens:**

- `is_public` Check field on `Insights Chart v3` and `Insights Dashboard v3`;
  toggled from `ChartShareDialog.vue` / `DashboardShareDialog.vue`, persisted via
  `update_access` (`insights_dashboard_v3.py:202`).
- The share URL carries the plain doc name (`getShareLink()` in
  `frontend/src2/charts/chart.ts:432` and `dashboard/dashboard.ts:322`); there is
  no signed/expiring token. `insights.api.shared.get_chart_name`/
  `get_dashboard_name` (allow_guest) resolve renamed docs via `old_name`.
- Guest data access is centralized in `insights/api/shared.py`:
  `is_public(doctype, name)` walks the graph — a public dashboard makes its
  charts public (`get_public_charts()`), and a public chart makes its linked
  queries public (`is_public_query`, checks `query` and `data_query`).
- One header-based token exists, but it is internal only:
  `X-Insights-Preview-Key`, a short-lived cache key generated by
  `generate_preview_key()` (`insights_dashboard_v3.py:323`) so the server can
  screenshot its own dashboard for the preview image. Not a sharing mechanism.

**Guest execution path** (`insights/api/__init__.py:172-240`):

- `insights.api.get_doc` and `insights.api.run_doc_method` are
  `allow_guest=True`; on `PermissionError` they fall back to the `is_public`
  check and re-run with `ignore_permissions=True` under the
  `frappe.flags.insights_for_public_access` flag.
- Guests can only invoke a hardcoded method allowlist (`is_public_method`):
  `Insights Query v3.execute` / `download_results`,
  `Insights Dashboard v3.get_distinct_column_values` / `track_view`.
- The whole src2 frontend routes through these two wrappers
  (`frontend/src2/helpers/resource.ts:18-22`), so shared views reuse the normal
  chart/dashboard components unchanged.

### 2. iframe embedding — verified in code, shipped (minimal)

- The share dialogs generate a copyable iframe snippet
  (`ChartShareDialog.vue:16`, `DashboardShareDialog.vue:22`) — it is just the
  `/shared/...` URL wrapped in `<iframe>`, so it inherits the public-flag model
  above; no embed-specific params (no theme, no filter passthrough, no
  chromeless flag).
- Cross-origin framing is controlled by `Insights Settings.allowed_origins`:
  `InsightsPageRenderer.set_headers` (`insights/utils.py:185`) emits
  `Content-Security-Policy: frame-ancestors 'self' <origins>` on `/shared`
  pages. Same-origin (desk embedding Insights) needs no config.
- Nothing else: no embed SDK, no postMessage protocol, no resize handshake.

### 3. Workspace custom-block embed experiment — not found in code

- No custom-block or iframe-embed code exists in the insights repo (grep for
  `custom_block` / `Custom HTML Block` / iframe across `insights/`,
  `frontend/src2/`, `docs/`: only the share dialogs above). The
  `fork/embedded-dashboards` branch is stale — zero commits beyond develop.
- The experiment (template dashboards embedded in module workspaces via
  Workspace Custom Block + chromeless iframe, live queries, same-site session)
  was ratified in discussion 2026-07-30 but has not been started.
- What shipped instead, as the first step, is a **link-out nudge**:
  `insights/public/js/insights_nudge.bundle.js` (via `app_include_js`,
  `hooks.py:44`) renders a banner on the Selling/Buying/Stock/Accounting
  workspaces pointing Insights Admins at the matching template dashboard
  (`/insights/template/insights/<template>`), with telemetry events
  (`workspace_dashboard_nudge_shown/clicked/dismissed`) to measure demand.
- Relevant framework primitive already exists: `frappe.create_shadow_element`
  (`frappe/public/js/frappe/dom.js:386`) is what Workspace Custom Blocks use to
  render — see framework item 1.

### 4. Whitelisted APIs a consumer app could call today — verified in code

- **Generic doc plumbing (the only guest-capable surface):**
  `insights.api.get_doc(doctype, name)` and
  `insights.api.run_doc_method(method, docs, args)` — fetch a chart/dashboard/
  query doc and execute it. This is exactly how the shared/embed views render,
  so a consumer app could drive the same path. Data comes from
  `Insights Query v3.execute(active_operation_idx, adhoc_filters, force, page,
  page_size)` (`insights_query_v3.py:153`), which returns
  `{rows, columns, sql, time_taken, total_row_count}` with a 10-minute result
  cache.
- **Everything else requires the `Insights User` role**: ~46 endpoints across
  `insights/api/*.py` are decorated `@insights_whitelist()`
  (`insights/decorators.py:142` — `frappe.whitelist` + role check). Relevant to
  a consumer: `insights.api.dashboards.get_dashboards` / `get_recent_dashboards`
  (listing with permission filtering), `insights.api.workbooks.get_workbooks`.
- **Templates as an integration surface (shipped, cross-app):** the
  `insights_workbook_templates` hook (`hooks.py:33` area) lets any app ship
  workbook templates; `insights.api.templates.get_workbook_templates` /
  `create_workbook_from_template` / `update_workbook_from_template` manage the
  one-shared-copy-per-site model. This is today's only "app ships a dashboard"
  mechanism.
- **Not found:** no purpose-built "render chart X" or "get chart data" endpoint
  for consumers — a consumer must fetch the chart doc, follow its `data_query`
  link, and call `execute` on the query, i.e. it must understand Insights'
  doc model.

## Framework

### 1. Shadow-DOM "vue islands" POC — found in PR/branch, verified in code (not merged)

- PR **frappe/frappe#39773** "feat: `frappe-ui` based vue app (vue-islands) in
  desk (wip)" — author nextchamp-saqib, branch `frappe-ui-desk-poc` (local),
  base `develop`, opened 2026-06-04, **still open, untouched since**.
- Verified on the local branch — a complete working POC:
  - `frappe/public/js/frappe/ui/vue_island.js` — `mountVueIsland()` /
    `frappe.ui.mount_vue_island`: attaches an open shadow root, injects the
    island's CSS bundle into the shadow, mounts the Vue app with a
    memory-history router (frappe-ui components call `useRouter()`
    unconditionally), provides `frappe-ui:portal-target` as an *element* inside
    the shadow so reka-ui overlays render in the styled tree, reuses desk
    globals via `SetVueGlobals`, and handles soft hot-reload via a WeakMap of
    wrapper → app.
  - Parallel **Vite** build pipeline for `frappe/public/js/islands/*.bundle.js`
    (`esbuild/build-islands.mjs`, IIFE output so `frappe.require` works, shared
    `assets.json`); `esbuild/postcss-root-to-host.js` rewrites `:root` design
    tokens to `:host` (`:root` never matches inside a shadow root).
  - POC desk page `frappe-ui-poc` exercising Button, Dialog, Popover, Combobox,
    FormControl etc. from the frappe-ui barrel. **No charts in the POC.**
  - Plan doc `PLAN-FRAPPE-UI-DESK.md` on the branch (status "proposed").
- Limitations visible in code/plan: each island duplicates the full frappe-ui
  CSS in its shadow root (adoptedStyleSheets flagged as follow-up); dark mode
  hardcoded to light; overlay portal contract needs frappe-ui patches (dep is
  `link:./frappe-ui`, patches to Popover/TimePicker not yet upstreamed); Toast,
  TextEditor popovers, and echarts `appendToBody` are outside the portal
  contract; dual-watcher `assets.json` orchestration unresolved.
- Already on develop (unrelated, simpler): `frappe.create_shadow_element`
  (`frappe/public/js/frappe/dom.js:386`) — the shadow-DOM helper Workspace
  Custom Blocks use; raw html/css/js, no Vue, and it links *desk* CSS into the
  shadow (the opposite intent).

### 3. Standard DuckDB sync — verified in code + merged PRs; shipped, snapshot-based

- **Merged**: PR frappe/frappe#40177 "feat: Duckdb integration" (ruthra-kumar,
  merged into develop 2026-06-25), backported to **version-15-hotfix** (#40798)
  and **version-16-hotfix** (#40795), both merged 2026-07-13. Follow-ups:
  #40929 fixes (July), #41150 "unbuffered sync from mariadb to duckdb"
  (merged 2026-07-23, backported #41185/#41186). `duckdb~=1.4.3` is a hard
  dependency in frappe's `pyproject.toml`.
- Design (verified in local code, present on the develop-based branch):
  - Doctypes: `DuckDB Sync` (submittable; one `.duckdb` file per synced doctype
    under the site's **private files**), `DuckDB Sync Item`, `Doctype To Sync`
    (child table on **Report**), `Synced Report Settings`.
  - Sync mechanism: DuckDB `ATTACH`es MariaDB directly and does
    `INSERT INTO ... SELECT` per table, one self-chaining long-queue job per
    table with `skip_locked` row claims (`frappe/core/doctype/duckdb_sync/
    duckdb_sync.py`); parent doctype + all its child tables auto-included.
  - **Report-driven, snapshot-based**: `Report.snapshot_report` +
    `doctype_to_sync` decide what syncs; a Scheduler Event (created from System
    Settings → Advanced, default Daily) submits fresh `DuckDB Sync` docs;
    `cleanup_old_syncs` deletes snapshots older than 7 days. Full-table copy,
    **not incremental/delta** (despite earlier delta-sync talk). Script report
    boilerplate gains `execute_snapshot_report(filters)`;
    `frappe.desk.query_report.run` returns `snapshot_report`/`snapshot_at` so
    the UI can show freshness.
  - Gaps visible in code: literal `# TODO: permissions` in the sync job; no
    connection whatsoever to Dashboard Chart — this integrates with **Report**
    only.
- Timeline signal: main body June 2026, refinements and backports through late
  July 2026 — active, and already on v15/v16 hotfix branches.

### 4. Desk Dashboard / Dashboard Chart — verified in code

- Doctypes at `frappe/desk/doctype/`: `dashboard`, `dashboard_chart`,
  `dashboard_chart_source`, `dashboard_chart_field`, `dashboard_chart_link`,
  `dashboard_settings`, `workspace_chart`.
- Rendering path (two entry points):
  1. Dashboard page: `frappe/core/page/dashboard_view/dashboard_view.js` →
     `dashboard.get_permitted_charts` / `get_permitted_cards` →
     `frappe.widget.WidgetGroup`.
  2. Per-doctype dashboard list view:
     `frappe/public/js/frappe/views/dashboard/dashboard_view.js`
     (extends ListView; public charts for that doctype + per-user
     `dashboard_settings` customization).
  Both funnel into `frappe/public/js/frappe/widgets/chart_widget.js` →
  `frappe.utils.make_chart` (`utils.js:1472`) → **frappe-charts 2.0.0-rc27**
  (`frappe/public/js/frappe/ui/chart.js`). echarts appears nowhere in desk.
- Data fetch, selected per `chart_type` in `chart_widget.js:839-871`:
  `Custom` → the source's own method from the `frappe.dashboards.chart_sources`
  registry; `Report` → `frappe.desk.query_report.run`; everything else →
  `frappe.desk.doctype.dashboard_chart.dashboard_chart.get` (whitelisted,
  `@cache_source`, dispatches to group-by/heatmap/timeseries config builders).
- Extension points:
  - **`Dashboard Chart Source`** doctype — developer-mode-gated, module-owned
    `.js` file on disk that registers `{method, filters}` into
    `frappe.dashboards.chart_sources`; six shipped sources (e.g.
    `frappe/desk/dashboard_chart/login_activity/`). This is the closest thing
    to a pluggable chart-data provider in desk today.
  - `custom_options` JSON on Dashboard Chart, deep-merged into frappe-charts
    args (`chart_widget.js:667`).
  - Report-backed charts via `report_utils.make_chart_options`.
  - Workspace charts: `workspace_chart` doctype + editor.js block
    (`views/workspace/blocks/chart.js`); Workspace **Custom Blocks** render via
    `frappe.create_shadow_element` (`custom_block_widget.js`) — the natural
    slot for the Insights embed experiment.
  - Permission hooks: `get_permission_query_conditions` / `has_permission`
    registered in `frappe/hooks.py:112-134`.
- Side note: `frappe/public/js/frappe/ui/components/` (21 vanilla-JS
  components, July 2026, Nikhil Kothari) is a separate "modernize desk without
  Vue" track — no shadow DOM, no frappe-ui.
