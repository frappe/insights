# Every test names the feature it pins

Date: 2026-09-14

## Status

Accepted.

## Context

Agents write most tests now, and each one pins the rule it was written beside. The suite grew to 1,208 cases across three layers with no denominator: nobody could say what share of the product had a test, or which layer a new test belonged to. The e2e areas already used flow-sentence titles as their inventory, but the backend and unit suites had no such list, and the three were never read together.

Prior art was surveyed first (`docs/projects/test-strategy/research/`, archived). Every hand-kept feature matrix found had drifted. The ones that survive are generated from annotations on the tests and diffed in CI. No repo states "one e2e per feature"; the ones with rules say the opposite.

## Decision

**A feature list is the denominator, and the tests carry the mapping.**

- `docs/features.md` is hand-written: one row per thing a user does or relies on, slug `<area>.<feature>` in glossary words, sentence in user words. A feature row precedes its first test.
- Every test carries a directive on the line above it, `# @feature <slug>` or `// @feature <slug>`, one syntax for all three layers.
- `docs/coverage.md` is generated by `insights/tests/features.py` and diffed in CI. Nobody edits it. A test without a directive, or a slug not in the list, fails lint.
- A test goes to the lowest layer that can observe the behaviour. The check is "does this need a browser?" A high-level failure with no low-level failure means a low-level test is missing.
- E2E stays few and long. A case whose only assertion is that something renders is a unit test in the wrong layer. Controls are not features; what a control achieves is.

Rejected: a hand-maintained coverage column (drifts); Gherkin (the sentence titles carry the benefit without the step layer); one e2e per feature, or per control (no BI suite does it, and the flake cost grows with the count).

## Consequences

The convention agents and the review bot read is `docs/agents/testing.md`. Adding a feature is two edits: the row, then the test. Renaming a slug touches every test that names it, so slugs use glossary nouns that do not move. Migrations live under `upgrade` and suite infrastructure under `tooling`, so nothing is undirected.
